Case study 03 · Document workflow automation

Automating document matching and Oracle ERP insertion.

Estimation AI identifies, matches, validates, and stores related estimation, mixing-sheet, and purchase-order PDFs within one controlled document-to-ERP workflow.

The operational problem

Related PDFs had to be found, checked, and entered one by one.

Employees manually opened documents, searched for estimation numbers, matched related files, checked whether records already existed, and inserted each document into the ERP workflow.

The difficult part was preserving the relationship between files while preventing incomplete groups, incorrect identifiers, and duplicate Oracle records.

A real failure, fixed

Real scans failed five ways. Every check stayed in place.

Some customer purchase-order scans couldn’t be inserted. The upload stopped with “AI document analysis found no Estimation No. values”, and staff entered those orders into the ERP by hand.

Nine files from one batch (five distinct documents, three of which failed) were re-run through the app read-only, comparing what Azure returned with what Oracle holds. That showed five separate causes. Digits are masked here.

  1. 01

    A PO printed from an email

    Cause
    The page looked like email correspondence, so the whole page, EST / LM stamp included, was ignored.
    Fix
    A page carrying the EST NO / LM NO stamp counts as the PO itself.
  2. 02

    A stamp with a smudged header

    Cause
    A table was only recognized if its header read “EST NO / LM NO”.
    Fix
    The table is also recognized by its rows: a 6-digit EST followed only by an order number.
  3. 03

    An export contract with no stamp

    Cause
    Only a handwritten “Est: ###### / order no” was there, and nothing looked for that layout.
    Fix
    A labelled “Est:” note directly followed by an order number is accepted.
  4. 04

    A stamp printed over a “TOTAL” line

    Cause
    The LM cell read “LM###### TOTAL:” and failed the order cross-check.
    Fix
    The cell is reduced to the order number it holds.
  5. 05

    A handwritten 1 read as a slash

    Cause
    The order came out as “LM##/###”, which didn’t match the real one.
    Fix
    A slash between digits is read as 1.

Why it stays safe

  • Every extracted EST is still checked against Oracle’s EST-to-order mapping, so a wrong reading blocks the upload instead of attaching the PDF to the wrong order.
  • A smudged data row blocks the file instead of being skipped.

Result

All nine files now resolve to the correct orders, in both the batch uploader and the pending-documents page. That was checked read-only, with nothing written to the database. 211 tests pass, 5 of them new, and the fix is deployed to production.

Architecture & safety

Matching is useful only when the database operation is dependable.

  • 01

    Identifier validation

    Extracted numbers are normalized, then cross-checked against Oracle’s estimation-to-order mapping before they are used for grouping.

  • 02

    Relationship checks

    The interface makes missing or unmatched documents visible before insertion.

  • 03

    Duplicate prevention

    Existing Oracle records are checked so the same document is not inserted twice.

  • 04

    Controlled Oracle storage

    Approved metadata and PDF files are written to the intended ERP document records.

Honest limitations

Document quality and business rules still matter.

  • OCR and identifier extraction can be affected by poor scans, unusual layouts, or damaged PDFs.
  • A badly misread handwritten digit still blocks the file for manual entry.
  • Ambiguous and unmatched files require human review before insertion.
  • Processing time depends on page count, file size, and the amount of validation required.
  • The details table was not part of the purchase-order extraction fix.
  • Public visuals are sanitized; client identity, document content, and production records remain confidential.
